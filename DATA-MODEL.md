# Модель данных

```
Country ──< City ──< Area ──< Place
                       │  └──< PhotoSpot  (areaId, + placeIds как связанные точки)
                       
Route ──< RouteStop ──> Place         (города маршрута выводятся из остановок)
Trip ──> City[]                       (страны поездки выводятся из городов)
UserState.assignedRoutes: { tripId, routeId, date }
```

## Принципы
- **Каталог не зависит от поездки.** Страны, города, районы, точки, маршруты и фотолокации лежат в `assets/data/catalog/` и переиспользуются в любых поездках.
- **Поездка только ссылается на города** (`Trip.cityIds`). Допустимые маршруты для поездки: `ContentService.getRoutesForTrip(tripId)`.
- **Связи хранятся один раз.** Город точки — через `Place.areaId → Area.cityId`, города маршрута — через его остановки. Поля `cityId` на точке или маршруте нет, чтобы данные не расходились.
- **Фотолокация принадлежит району** (`PhotoSpot.areaId`), поэтому при фильтре по району показывается `getPhotoSpotsByArea(areaId)`. `placeIds` — опциональная связь с точками рядом.
- **Личные данные отдельно** (`UserState`, localStorage): статусы точек, заметки, назначения маршрутов на даты. Назначения привязаны к `tripId`.

## Миграция пользовательских данных
Ключ localStorage изменился на `trip-app.user-state.v2`. Старый ключ `japan-trip-user-state` читается один раз: назначенные маршруты получают `tripId = japan-2026`. Старая запись не удаляется.

## Проверка данных
`npm run validate:data` проверяет ссылки между сущностями (запускается автоматически перед `npm run build`). Ошибки останавливают сборку, предупреждения о контенте только выводятся.

## Свои данные поверх каталога (overlay)
- Каталог в `assets/data/catalog/` неизменяем. Всё, что вы добавили или изменили (страны, города, районы, точки, маршруты, фотолокации, поездки), хранится отдельно в `UserContentStore` (localStorage, ключ `trip-app.user-content.v1`) как записи `{ value, updatedAt }` по id.
- Запись с id из каталога **переопределяет** точку каталога. `value: null` — удаление (в том числе скрытие точки каталога). Так удаления тоже синхронизируются.
- `ContentService` склеивает каталог и overlay через сигналы, поэтому экраны обновляются сразу.
- Новые id имеют префикс `u-` (например, `u-place-...`).
- Фото хранятся в IndexedDB (`trip-app` / `photos`) по id фото, в модели точки только ссылки (`Place.photos`). Для фото из Wikimedia обязательны автор и лицензия, они показываются под фото.

## Личные отметки и план (`UserState`, версия 3)
- Отметки (`placeStates`, `photoSpots`) — личные, у каждой записи `updatedAt`. Назначения маршрутов на дни (`assignedRoutes`, с пометкой `deleted`) и заметки — часть общего плана.

## Синхронизация между устройствами
- Страница `/sync`: экспорт в файл `trip-planner-YYYY-MM-DD.json` (опционально с фото) и импорт с предпросмотром.
- Слияние по записям: побеждает более свежий `updatedAt`, более новые правки на устройстве не затираются, повторный импорт того же файла ничего не меняет.
- Отметки «Хочу / Был / Избранное» применяются только если при импорте включён чекбокс, иначе остаются локальными.
- Это обмен файлами, а не автосинхронизация: при одновременных правках нужно обменяться файлами снова.

## Подтягивание данных по ссылке
- Из ссылки Google Maps читаются только название и координаты (без API). Короткие ссылки `maps.app.goo.gl` браузер раскрыть не может.
- Остальное берётся из открытых источников: OpenStreetMap/Nominatim (адрес, часы, сайт, категория; атрибуция «© OpenStreetMap contributors» хранится в `Place.sources`) и Wikimedia Commons (фото с автором и лицензией). Данные из Google не сохраняются.
- Всё необязательно: при недоступности сервисов поля заполняются вручную.

## Тесты
- Чистая логика (разбор ссылок, OSM/Commons, слияние и импорт) покрыта спеками `*.spec.ts` в `core/utils/`.

## Маршруты
- Маршрут — упорядоченный список остановок (`RouteStop`: точка, приоритет, время на месте, транспорт до следующей точки). Города маршрута выводятся из остановок.
- Транспорт относится к отрезку «эта остановка → следующая». При перестановке, удалении или упорядочивании отрезки, у которых сменился сосед, сбрасываются автоматически, чтобы не оставалось неверного времени в пути.
- Любой маршрут можно менять: правка каталожного маршрута сохраняется как overlay-запись (можно «Вернуть исходный»), свои маршруты имеют id `u-route-...`. Все правки синхронизируются через экспорт и импорт.
- Список маршрутов сортируется по `RecommendationService` (не посещённые и избранные точки, уже назначенные дни).
- Назначение на день: `UserState.assignedRoutes` (`tripId`, `routeId`, `date`). Экран «Дни» будет строиться на этих данных.
- Чистая логика маршрутов (изменение состава, итоги, ссылка Google Maps, упорядочивание по ближайшему соседу) находится в `core/utils/route-utils.ts` и покрыта спеками.

## Дни, погода и видимость Фудзи
- Главный экран `/days`: карточки дней поездки с погодой, оценкой видимости Фудзи, назначенными маршрутами и предупреждениями. Маршрут на день выбирается диалогом (самые подходящие сверху), его можно убрать или перенести.
- Погода берётся из Open-Meteo (бесплатно, без ключа, ссылка на источник показывается в приложении). Для дат в пределах 16 дней используется прогноз. Для более поздних дат показывается климат тех же дат за 5 прошлых лет («видно в 3 из 5 лет»). Когда поездка приблизится, прогноз подтягивается сам.
- Результаты кэшируются в localStorage (`trip-app.weather.v1`): прогноз 3 часа, климат 30 дней. Без связи показываются последние данные с пометкой.
- Погода запрашивается для каждого города поездки с координатами (у пользовательских городов берётся центр их точек) и отдельно для района вершины Фудзи.
- В день используется город первого назначенного маршрута, иначе основной город поездки.
- Оценка видимости Фудзи (`core/utils/fuji.ts`) — эвристика 0–100 по часам: решают нижняя облачность у наблюдателя и облачность на высоте вершины (3,8 км), затем влажность (дымка, сильнее с расстоянием), осадки и туман, видимость (только в прогнозе). Оценка дня — лучшее трёхчасовое окно. Метки: ≥75 отлично, ≥55 скорее видно, ≥35 возможно, иначе вряд ли. Это ориентир, а не гарантия.
- Для климата показывается доля прошлых лет с оценкой ≥55.
- Предупреждения: маршрут «от погоды» в дождливый день, маршрут к Фудзи в день с плохой видимостью (с кнопкой «Перенести» на лучший день), насыщенный день (более 12 часов).

## Брони и документы
- Брони (`Booking`: перелёт или проживание) хранятся как отдельная overlay-коллекция `bookings` и привязаны к поездке (`tripId`). Время везде местное, как в документе, без пересчёта часовых поясов.
- Исходный документ (PDF, письмо) сохраняется на устройстве (IndexedDB) и прикрепляется к броне, поэтому открывается без интернета, например в аэропорту. При удалении брони документ удаляется, если им больше никто не пользуется.
- Брони и документы синхронизируются через экспорт и импорт (документы идут вместе с фото по галочке «Включить фото и документы»).

## Распознавание документов
- Всё происходит на устройстве, документы никуда не отправляются. Поддерживаются PDF (читается через pdf.js, он грузится только при открытии PDF), письма `.eml` (текст, вложенные PDF и календарь), календарь `.ics`, HTML и вставленный текст. Картинки и сканы без текстового слоя не распознаются (нужен OCR), для них есть ручной ввод.
- `core/utils/booking-parser.ts`: рейсы (номер рейса по списку авиакомпаний, аэропорты, даты и время, «+1», код брони) и проживание (метки Check-in/Check-out, Anreise/Abreise, Заезд/Выезд, название, адрес, код брони). Даты в форматах EN/DE/RU/ISO/японском. Если год не указан, берётся год поездки с предупреждением.
- Результат разбора всегда показывается на экране проверки: поля можно править, лишнее отключить, видны предупреждения и распознанный текст (его можно скопировать, чтобы улучшить разбор для нового формата).
- `suggestTripRange`: даты поездки по броням (первый приезд/заезд, последний выезд/вылет домой). Применяются кнопкой.
- На экране «Дни» показываются вылеты, прилёты, заезды, выезды, ночёвки и ночи без брони жилья. Город дня может определяться по отелю.
- Для хостинга: рядом с приложением должен отдаваться файл `pdfjs/pdf.worker.min.mjs` (копируется сборкой) с типом `text/javascript`.

## Что учтено по настоящим документам
- Билет Ozon Travel (три колонки: вылет, рейс, прилёт/пересадка; время стоит перед датой) и ваучер отеля (подписи Check-in/Check-out/Hotel/Address на отдельных строках, год не указан). На них видно, что **дата берётся рядом со временем на той же строке**, а не из шапки (дата выпуска билета), название отеля читается со строки под подписью «Hotel», код брони авиабилета с места под заголовком «BOOKING REF», номер заказа отеля после «order number … :».
- **Год по дню недели:** «1 December, Tuesday» без года подтверждается днём недели (1 декабря 2026 это вторник), поэтому предупреждение о годе не показывается. Если день недели не подходит ни к ближайшим годам, год остаётся предположением с предупреждением.
- Маршрут через несколько стран (Москва, Гуанчжоу, Токио, Нячанг): для поездки в Японию диапазон дат берётся от прилёта в Токио до вылета из Токио, перелёты вне страны поездки сохраняются как брони, но на даты поездки не влияют.
- В дне брони идут по времени: прилёт, заезд, вылет. Если рейс приземляется в тот же день, на одной строке видны оба времени.
- При непредвиденной ошибке чтения файла приложение показывает причину и блок «Технические детали» с кнопкой «Копировать для поддержки» (тип ошибки, браузер, имя файла).
